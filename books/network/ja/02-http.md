# 2. ブラウザと HTTP

ブラウザとサーバーの会話の決まりが **HTTP**（HyperText Transfer Protocol）です。ブラウザが「このページをください」と**リクエスト**を送り、サーバーが「どうぞ」と**レスポンス**を返す。Web のやりとりは全部この形です。

## URL の読み方

**URL** は、「どのサーバーの、どのデータを、どの方法で」取りに行くかを1行で書いたものです。

```text
https://example.com:443/news/list.html?page=2#top
```

| 部分 | 例 | 意味 |
| --- | --- | --- |
| スキーム | `https` | どの方法で取りに行くか。`https` は暗号にした HTTP（9章） |
| ホスト名 | `example.com` | どのサーバーか。DNS で IP アドレスに変える（3章） |
| ポート番号 | `443` | サーバーのどのアプリか（4章）。`https` なら 443、`http` なら 80 で、ふつうは書かない |
| パス | `/news/list.html` | サーバーの中のどのデータか |
| クエリ | `?page=2` | サーバーにわたす追加の値。`&` でつなぐ |
| フラグメント | `#top` | ページの中の場所。サーバーには送らず、ブラウザだけが使う |

## リクエストとレスポンス

HTTP/1.1 のやりとりは、ただの文字です。`curl -v` で中身を見られます（`>` が送ったもの、`<` が受け取ったもの）。

```bash
curl -v http://example.com/ -o /dev/null
```

```text
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.18.0
> Accept: */*
>
< HTTP/1.1 200 OK
< Content-Type: text/html; charset=utf-8
< Server: cloudflare
< Age: 13682
< cf-cache-status: HIT
```

- **リクエスト**: 1行目が「**メソッド** パス バージョン」。次の行から**ヘッダー**（`名前: 値`）が並び、空の行で終わる。POST などではそのあとに**ボディ**（送るデータ）が続く
- **レスポンス**: 1行目が「バージョン **ステータスコード** 説明」。ヘッダーのあと、空の行をはさんで**ボディ**（HTML や画像そのもの）が続く

`Host:` があるので、1台のサーバー（1つの IP アドレス）で、いくつもの名前のサイトを分けて返せます。

### よく使うメソッド

| メソッド | 意味 | 例 |
| --- | --- | --- |
| `GET` | データをもらう | ページを開く、画像を読む |
| `POST` | データを送って、何かしてもらう | フォームを送る、センサーの値を送る |
| `PUT` / `PATCH` | データを置きかえる / 一部を変える | 設定を変える |
| `DELETE` | データを消す | 記録を消す |
| `HEAD` | ヘッダーだけもらう | 大きさや更新日だけ知りたい（`curl -I`） |

### ステータスコード

最初の数字で、だいたいの意味がわかります。

| コード | 意味 | よく見るもの |
| --- | --- | --- |
| 2xx | うまくいった | `200 OK` |
| 3xx | 別の所を見て | `301 Moved Permanently`（引っ越した）、`304 Not Modified`（前のをそのまま使って） |
| 4xx | **頼んだ側**のまちがい | `400` 書き方がおかしい、`401` ログインして、`403` 見せられない、`404 Not Found` ない |
| 5xx | **サーバーの側**のトラブル | `500` サーバーの中のエラー、`502`・`504` 奥のサーバーが答えない、`503` 混んでいる・休み中 |

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://example.com/nothing-here
```

```text
404
```

## ヘッダーでわかること

| ヘッダー | 向き | 意味 |
| --- | --- | --- |
| `Host` | リクエスト | どのサイトか |
| `User-Agent` | リクエスト | どのブラウザ・アプリか |
| `Cookie` | リクエスト | 前にもらった Cookie を返す（下） |
| `Content-Type` | 両方 | ボディの種類（`text/html`、`application/json`、`image/jpeg` など） |
| `Cache-Control` | レスポンス | どのくらいのあいだ、手元に取っておいて使ってよいか |
| `Set-Cookie` | レスポンス | ブラウザに Cookie を覚えさせる |
| `Location` | レスポンス | 3xx のときの、引っ越し先 |

## HTTP は「覚えていない」: Cookie

HTTP は、1回1回のやりとりが別々で、前のリクエストを覚えていません（**ステートレス**）。それでもログインしたままでいられるのは **Cookie** のおかげです。

1. ログインに成功すると、サーバーが `Set-Cookie: session=abc123` を返す
2. ブラウザはそれを覚えて、同じサイトへのリクエストに毎回 `Cookie: session=abc123` を付ける
3. サーバーは、その値で「さっきログインした人だ」とわかる

Cookie を盗まれると、その人になりすませます。だから HTTPS（9章）で暗号にすることが大事です。

## 1ページを開くと、何十回もリクエストする

HTML の中には、画像・CSS・JavaScript・フォントへのリンクがあります。ブラウザは HTML を読みながら、それらを1つずつ取りに行きます。大きなニュースサイトなら、1ページで100回をこえることもあります。

パソコンの Chrome なら **F12**（開発者ツール）の「Network」タブで、全部のリクエストと、かかった時間・ステータスコード・ヘッダーを見られます。

## HTTP/1.1・HTTP/2・HTTP/3

| 版 | 年 | 特ちょう |
| --- | --- | --- |
| HTTP/1.1 | 1997 | 文字でやりとり。1本の TCP では1つずつ順番に |
| HTTP/2 | 2015 | 1本の TCP の中で、たくさんのリクエストを同時に流す。ヘッダーを縮める |
| HTTP/3 | 2022 | TCP ではなく **QUIC**（UDP の上、4章）を使う。つなぐのが速く、スマホが Wi-Fi から 4G/5G に切り替わっても切れにくい |

アプリから見た意味（メソッド・ステータスコード・ヘッダー）は同じで、運び方だけがちがいます。

## Web API: アプリどうしも HTTP で話す

HTTP はブラウザのためだけのものではありません。スマホのアプリや IoT の機械も、HTTP で JSON を送ったり受け取ったりして、サーバーの機能を使います。これを **Web API** といいます。

```bash
curl -s -X POST -H "Content-Type: application/json" \
     -d '{"barn": 1, "temp": 21.5}' https://httpbin.org/post
```

```text
{
  "headers": {
    "Content-Length": "25",
    "Content-Type": "application/json",
    "Host": "httpbin.org",
    ...
  },
  "json": {
    "barn": 1,
    "temp": 21.5
  },
  "method": "POST",
  "origin": "203.0.113.45",
  ...
}
```

httpbin.org は、受け取ったリクエストをそのまま返してくれる、試すためのサーバーです。`origin` は、サーバーから見えたこちらの IP アドレス（7章の、家のルーターのグローバル IP アドレス）です。

## 最初の Web サーバー

![CERN で最初の Web サーバーになった NeXT のコンピューター](images/first-web-server.jpg)

1990年、ティム・バーナーズ＝リーは CERN の NeXT のコンピューターで、最初の Web サーバーとブラウザを動かしました。本体には「このマシンはサーバーです。電源を切らないで!!」という紙が貼ってありました。

## まとめ

- URL は「スキーム・ホスト名・ポート・パス・クエリ」
- HTTP はリクエスト（メソッド・ヘッダー・ボディ）とレスポンス（ステータスコード・ヘッダー・ボディ）のやりとり
- 4xx は頼んだ側、5xx はサーバーの側の問題
- HTTP は前のやりとりを覚えていないので、ログインは Cookie で続ける
- アプリや IoT の機械も、Web API で HTTP を使う

## 練習問題

```quiz
Q: データをもらうときに使う HTTP のメソッドは何ですか。
A: GET
E: データを送って何かしてもらうときは POST です。

Q: 「ページが見つからない」を表すステータスコードは何ですか。
A: 404
E: 4xx は頼んだ側の問題、5xx はサーバーの側の問題です。

Q: https の URL で、ポート番号を書かないときに使われるポート番号は何ですか。
A: 443
E: http なら 80 です。

Q: HTTP は前のやりとりを覚えていません。ログインしたままにするために、ブラウザが毎回送り返すものは何ですか。
A: Cookie | クッキー | cookies
E: サーバーが Set-Cookie で渡し、ブラウザが Cookie ヘッダーで返します。

Q: HTTP/3 が TCP の代わりに使う、UDP の上で動くプロトコルは何ですか。
A: QUIC | クイック
E: つなぐのが速く、回線が切り替わっても切れにくいのが特ちょうです。
```
